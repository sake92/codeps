# codeps v2 spec: metrics report, no visualization

This describes a scope change to `codeps`, based on design discussion (not a
direct read of the current repo — verify against actual source before
implementing, especially around what the existing hierarchical JSON model and
cycle-grading code currently do, since names/structures below may not match
exactly).

**Core decision this spec implements:** drop the Cytoscape.js visual UI.
For a codebase with dozens of packages and cycles of 20-30+ members, a
node-link diagram of "a big ball of mud" doesn't read as structure — it reads
as noise. Graphs earn their keep when there IS structure to show (a call
sequence, a small cluster). Here the output that matters is a ranked list an
agent or human can act on. `codeps` becomes a single CLI command that emits
structured data, full stop.

---

## 1. Remove

- **Cytoscape.js UI / two-screen web frontend.** Delete entirely. No
  client-side rendering, no layout engine, no "black hole" styling — all of
  that was mockup work for a visualization that's being cut.
- **Any function/type/method-level nodes in the dependency graph.** codeps
  operates at exactly two granularities: **package** and **file**. Granular
  (type/member) nodes stay *internal* to the parsers — `export` collapses them
  to package/file nodes via the aggregator (`Aggregator.fileLevel`) at write
  time, so the output graph and the metrics never see them. Method/function
  internals are a different tool's job (complexity analysis), not codeps's.
- **Hierarchical multi-level export** beyond package → file. Don't build or
  maintain a deeper nesting (e.g. package → file → symbol) in the output
  model.
- **DSM (Design Structure Matrix) rendering**, if any exists — out of scope,
  decided earlier.
- **Any git/churn integration** — stays out. That's `xray`'s job (a separate
  tool), not codeps's. codeps is static-graph-only, always.

## 2. Keep

- **SemanticDB-based extraction for Scala/JVM** — this is codeps's actual
  differentiator (post-typecheck precision for implicits/macros vs. naive
  import parsing). Keep as the Scala/JVM extraction backend.
- **Tarjan SCC cycle detection** — keep the algorithm, but see §4 for the
  exact contract it needs to satisfy (recomputable on a mutated edge list,
  stable/deterministic component keys — see "SCC key" below).
- **Package-level and file-level graph construction** — keep both
  granularities as first-class scopes.
- **Existing hierarchical JSON internal model**, if there is one, can stay as
  an *internal* representation used to build the node/edge lists — but the
  **output format** to the user is the flat report described in §5, not this
  internal model directly.

## 3. Not in scope now: keep the interface language-agnostic

**Do not implement TS/Python support.** Scala/JVM via SemanticDB is the only
extraction backend to build. The only requirement here is that the report
schema (§5) and the metrics in §4 don't bake in anything Scala-specific by
name — they operate on a generic node/edge list plus a per-node
`is_exposed`/`ports`/`mut_ports` set of flags, computed by whatever
extraction backend produced them. That way, if a TS or Python extractor gets
built later (not now, not part of this task), it only has to emit the same
generic JSON shape into the same metrics code — it doesn't require touching
§4 at all.

Concretely: the extraction backend's job is to turn source into
`{nodes: [...], edges: [...]}` with ports/mut_ports/is_exposed already
resolved per node. The metrics code in §4 must never assume Scala syntax
(`sealed`, `given`, `var`) beyond the Scala extraction backend itself —
those weight rules live in the Scala adapter, not in the generic metrics
layer. This is a "don't paint yourself into a corner" constraint on the
interface boundary, not a feature to build.

## 4. Metrics — exact definitions

All metrics are computed per scope (either the full package graph, or the
file graph within one selected package — same formulas apply to both, just
operating on that scope's node/edge set).

### Graph primitives

- **`fan_in(node)`** = count of distinct edges where `node` is the target.
- **`fan_out(node)`** = count of distinct edges where `node` is the source.
- Compute both by iterating the edge list once and incrementing counters —
  do not hand-author or cache these anywhere separate from the edge list.
  They must always be *derived*, never stored independently, or they will
  drift when edges are cut (see §6, live cut simulation).

### Exposed surface

- **`ports(node)`** = weighted count of exposed (`is_exposed == true`)
  members of `node`, using these weights:
  - `3` per exposed type/trait/class/interface (or TS `interface`/`type`,
    Python `class`)
  - `1` per exposed function/method/def/val
  - `0.5` per exposed member if it belongs to a `sealed` hierarchy (Scala
    `sealed trait`/`sealed class` — external code cannot add new
    subtypes, so the effective exposed surface is smaller than the raw
    member count suggests)
  - `+1` flat, once per `given`/`implicit` instance exposed by the node
    (these are "ambiently public" — reachable via implicit search without
    being explicitly referenced, so they deserve separate accounting, not
    folding into the type/def weight above)
- **`mut_ports(node)`** = count of exposed **mutable** state: a `var`
  declaration in exposed position, or an exposed `val` whose type is a known
  mutable collection (e.g. `scala.collection.mutable.*`, or language
  equivalents — a mutable list/dict/map instance exposed via a getter).
  These are counted separately from `ports` because they represent a
  coupling channel that doesn't show up as a graph edge at all (callers can
  depend on order-of-mutation without any static reference existing between
  them).
- **`exposure(node)`** = `ports(node) + mut_ports(node) * 3`. Single sort key
  combining both — mutable ports weighted 3x because they're a hidden
  channel on top of being exposed at all. Always report `ports` and
  `mut_ports` alongside `exposure` in output; never emit `exposure` alone,
  since the breakdown matters for deciding what to actually fix.
- **`utilization(node)`** = `fan_in(node) / ports(node)` if `fan_in(node) > 0`,
  else `null`. Do not compute for zero-fan-in nodes — a `null`/`—`
  utilization is itself meaningful (see "orphans" below), not a 0.

### Cycles (SCCs)

- Run **Tarjan's strongly connected components** algorithm on the current
  scope's node/edge list. Only components with **more than 1 member** count
  as a "cycle" — singleton components are just acyclic nodes, don't report
  them as SCCs.
- **SCC key**: derive as `"scc:" + min(member_ids)` (lexicographically
  smallest member id in the component), NOT a sequentially-assigned counter.
  This matters because the report gets recomputed after simulated/applied
  cuts (§6) — a counter-based id would renumber unpredictably across
  recomputation, while the min-id-derived key stays stable unless that
  specific member leaves the component. Stability here matters for anything
  downstream that diffs reports over time (the snapshot/PR loop from earlier
  design discussion).
- **`scc_size`** = member count.
- **`scc_members`** = a **closed cycle path** through the smallest member:
  the first node repeated at the end. When the SCC contains several
  interlocking cycles, `scc_size` may exceed the path length — the path
  shows one of the cycles; `scc_size` counts the full SCC membership.
- **`scc_ext_fan_in`** = count of edges where the target is in the SCC and
  the source is NOT in the SCC (i.e., dependents from outside the cycle).
  This is the "how much outside stuff is exposed to this cycle's blast
  radius" number — rank cycles by `scc_size` first, `scc_ext_fan_in` as a
  tiebreaker/secondary weight.

### Cut candidates (simulated, resolved-only)

For each SCC, edge "weight" = a proxy for how load-bearing/expensive the
dependency is (call-site count is the honest source if available from
SemanticDB extraction; if not available yet, a placeholder weight of 1 per
edge is acceptable but should be flagged as a known gap, not silently
treated as meaningful).

Algorithm per SCC:

1. Filter edges to **internal** edges only: both endpoints in the SCC's
   member set. (Do not suggest cutting any edge that isn't literally inside
   the cycle — external edges are irrelevant to resolving this specific
   cycle.)
2. For each internal edge: **remove it from a copy of the edge list**, rerun
   Tarjan, and check what happened to the component containing the edge's
   endpoints. **Only report the edges whose removal *resolves* the SCC** —
   i.e. the endpoints end up in no multi-member component. Edges that merely
   shrink the cycle (`partial`) or leave it unchanged (`none`, e.g. a chord
   running the ring's direction — redundant with the rest of the cycle) are
   deliberately *not* listed: they don't dissolve the cycle, and a naive
   "lowest weight = best cut" heuristic gets this wrong — showing only
   resolving cuts is the entire point of doing the simulation.
3. Report the resolving edges sorted by weight ascending, top N (6 is the
   default).
4. **`min_cuts_estimate`**: greedily apply the best `resolved`-or-largest-
   `partial` candidate, recompute the SCC on the now-mutated trial edge
   list, repeat against the shrunk component, until size reaches 1 or no
   candidate improves it. Report the count of cuts this took. This is a
   greedy heuristic, not a guaranteed-minimum feedback-edge-set solution —
   don't claim it's optimal, just report it as an estimate. (Internally this
   loop may use `partial`/`none` classifications; only the *reported*
   `cut_candidates` list is restricted to resolving edges.)

### Whole-repo / whole-scope metrics

- **`orphans`**: nodes where `fan_in == 0 AND fan_out == 0`. Zero
  additional computation beyond fan_in/fan_out already computed above —
  just filter. These are dead-code-removal candidates (step 1 of the
  improvement loop discussed earlier), report as their own list.
- **`critical_path_length`**: build the **condensation graph** (collapse
  each SCC to a single node, keep all other nodes as-is, re-wire edges
  between components accordingly, drop self-loops created by the
  collapse). This condensation is guaranteed acyclic. Find the longest
  path through it (standard longest-path-in-a-DAG via topological sort +
  relaxation, O(V+E)). Report as a single integer (path length in number of
  edges) — this is the structural lower bound on best-case parallel build
  time, independent of whether cycles exist, since even a fully acyclic
  graph has a depth floor.

## 5. Output contract

Single command: `codeps report --scope <packages|files> [--pkg <name>]
[--format <json|table>]`.

- `--scope files` requires `--pkg <name>` (the package to descend into).
- `--scope packages` ignores `--pkg`.
- Default format: `table`. `json` is the machine-readable rendering of the exact same
  computed data — do not compute anything differently between formats.

JSON shape:

```json
{
  "scope": "packages",
  "generated_at": "<ISO8601 UTC, second precision, e.g. 2026-08-27T10:00:00Z>",
  "summary": {
    "nodes": 100,
    "edges": 214,
    "nodes_in_cycles": 34,
    "orphans": 3,
    "critical_path_length": 7
  },
  "cycles": [
    {
      "id": "scc:cache",
      "members": ["cache", "scheduler", "cache"],
      "size": 2,
      "ext_fan_in": 5,
      "min_cuts_estimate": 1,
      "cut_candidates": [
        { "edge": ["scheduler", "cache"], "weight": 4 }
      ]
    }
  ],
  "surface": [
    { "node": "cache", "fan_in": 3, "fan_out": 2, "ports": 9, "mut_ports": 5, "exposure": 24, "utilization": 0.33 }
  ],
  "orphans": ["DeadUtil.scala"]
}
```

`table` format renders the same fields as plain aligned text — see prior
conversation for an example layout (cycles sorted by size desc, surface
sorted by utilization asc).

## 6. Notes for the implementing agent

- `fan_in`/`fan_out`/SCCs/cut simulations must all be **derived fresh from
  the current edge list on every run** — never cache or hand-author these
  fields anywhere. This is what makes the cut-simulation logic (§4) correct:
  it works by literally removing an edge from a copy of the list and
  recomputing, and that only produces trustworthy results if nothing else
  in the system is treating degree/SCC membership as separately-stored
  truth.
- Keep the language adapter interface (`is_exposed`, barrel resolution,
  extraction into package/file node+edge lists) as the seam between
  language-specific code and the metrics code in §4 — the metrics
  themselves must be language-agnostic once they receive a node/edge list
  with `is_exposed` flags already resolved.
- Everything in §4 is O(V+E) or close to it except the cut-simulation loop,
  which reruns Tarjan up to N times per SCC (N ~6) plus up to `min_cuts_estimate`
  times for the greedy loop — bound this (e.g. skip simulation for cycles
  above some size threshold, or cap total simulation reruns per report) if
  performance becomes an issue on large repos, but don't pre-optimize this
  before it's measured to be slow.
